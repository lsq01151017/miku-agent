# 初音未来 Agent —— Heart Heart Heart（Lv1 + Lv2）

> **这是「版本一」**：Python 单体实现，路径 `D:\二面\my-agent`。
> 「版本二」在 `D:\二面\cortico`（TypeScript + Cortico 框架），一键启停是 `D:\二面\启动她.bat`。
> 两个版本的差别与目录说明见 `D:\二面\README.md`。本文以下内容只描述版本一。

一个具有**持续状态、人格、记忆和行动能力**的智能角色 Agent。
本地模型负责人格与情感（Lv1），云端 API 负责真实行动（Lv2）。
本文件说明设计取舍与验证方式，供提交时作为设计文档使用。

> 题目原文：<https://join.geek-tech.club/problems2/heart-heart-heart>

## 1. 一句话架构

```
                         ┌──────────────────────────────────────────┐
   用户输入 ───────────► │ router.py  该回答，还是该行动？           │
                         │            关键词策略链 + 决策理由入日志   │
                         └───────────────┬──────────────┬───────────┘
                                         │ local        │ api
                    ┌────────────────────▼───┐   ┌──────▼─────────────────────────┐
                    │ Lv1  local_agent.py    │   │ Lv2  api_agent.py              │
                    │ Ollama deepseek-r1:14b │   │ DeepSeek deepseek-flash        │
                    │ · 人格（静态）          │   │ · tool calling                 │
                    │ · 情绪状态（动态）      │   │ · tools.dispatch() 真正执行     │
                    │ · 记忆注入              │   │ · 真实结果回传模型              │
                    │ · 流式输出              │   │ · 失败也能被"说出来"            │
                    └───────────┬────────────┘   └──────┬─────────────────────────┘
                                │                       │ 真实数据（事实）
                                │            ┌──────────▼──────────────────────┐
                                │            │ revoice：拟人化包装              │
                                │            │ 事实 → 初音未来的语气            │
                                │            └──────────┬──────────────────────┘
                                └───────────┬───────────┘
                                            ▼
                    ┌────────────────────────────────────────────────┐
                    │ memory.py   记忆生命周期系统                    │
                    │ 存储 / 检索 / 覆盖修正 / 遗忘 / 衰减 / 巩固      │
                    │ SQLite(memory.db) + JSON(state.json)           │
                    └────────────────────┬───────────────────────────┘
                                         ▼
                    ┌────────────────────────────────────────────────┐
                    │ logger.py   JSONL 审计（每轮一个 trace_id）      │
                    │ logs/agent_log.jsonl                           │
                    └────────────────────────────────────────────────┘
```

**混合架构的理由（为什么不让本地模型做工具调用）**：
14B 本地模型做 tool calling 的可靠性明显低于云端模型，而角色沉浸感的破坏往往就来自
"该查的时候没查、或假装查了"。所以按能力拆分职责：

| | 本地 `deepseek-r1:14b` | 云端 `deepseek-flash` |
|---|---|---|
| 负责 | 人格、语气、情感、陪伴 | 判断意图、调用工具、整理事实 |
| 不负责 | 事实性查询 | 最终对用户说的话 |
| 成本 | 免费、离线可用 | 只在需要行动时调用 |

**职责边界**：API 在"事实模式"下被明确要求**不要卖萌、不要自称初音未来**，
只输出客观事实；最终对用户说的话由本地模型用初音未来的语气生成。
这样"语言输出"和"系统行为"在数据流上就是两个可区分的概念 ——
正是题目 4.2 的要求。

## 2. Lv1：成为一个持续存在的角色

### 2.1 对话连续性
- 最近 `AGENT_HISTORY_WINDOW`（默认 8）轮**逐字**保留；
- 更早的对话被挤出窗口后，**总结成摘要**再进入上下文，而不是丢弃
  （`local_agent.ConversationHistory` + `context.compressed` 事件）；
- 全部对话落 SQLite（`conversations` 表），**重启进程后仍能续上**
  —— 记忆与状态都在磁盘上，程序退出不等于角色死亡。

### 2.2 人格：静态核心 + 动态状态
`config.py` 里的 `AGENT_PERSONALITY` 是你提供的设定原文，**永不重新生成**。
每轮 Prompt 由它叠加三层可变状态构成（`config.build_system_prompt`）：

```
AGENT_PERSONALITY（常量）
  + 关系状态（羁绊值 / 认识多少天 / 聊过多少轮）
  + 检索到的记忆
  + 当前情绪 → 翻译成"该怎么说话"
```

### 2.3 情绪 / 内部状态：六个连续维度
题目要求情绪"不应只依赖一句 prompt，而应该存在能被更新、读取，
并实际影响之后回复或行为的状态"。这里的答案是六个数：

| 维度 | 含义 | 对应人设 |
|---|---|---|
| `valence` 心情 | -1 难过 ～ +1 超开心 | 开心时哼歌 |
| `arousal` 活力 | 0 安静 ～ 1 蹦蹦跳跳 | 活泼、句尾语气词密度 |
| `bond` 羁绊 | 对制作人的亲近度 | 关系升级、更亲近 |
| `loneliness` 寂寞 | 想念程度 | **"怕寂寞"** |
| `shyness` 害羞 | 害羞度 | "呜……别这样盯着看啦" |
| `empathy` 关切 | 共情程度 | "用户情绪低落时先共情再鼓励" |

它们**真的在起作用**：
- `analyze_affect()` 每轮从用户输入 + 自己的回复里提取情绪变化，
  附**可读原因**（"「喜欢」→ 心情+0.35, 羁绊+0.11"）；
- 随时间向基线**衰减**（`begin_session` / `_decay`）；
- **离开越久，寂寞感自己上升**；超过 `AGENT_PROACTIVE_HOURS` 她会先开口
  （创新点「主动消息」）；
- 渲染成 `MOOD_DIRECTIVES` 的语气指令注入下一轮 Prompt；
- **情绪惯性**：单轮变化封顶 + 接近极值时的软饱和，
  避免连聊几句就把心情顶到 +1.00 后失去分辨力；
- 同一份状态也供 Lv3 的表情 / Lv4 的语音参数消费（`emotion_snapshot()`）。

情绪推导是**纯函数**（`config.mood_from_state`），优先级体现人设：
`关切 > 寂寞 > 害羞 > 闹别扭 > 低落 > 元气/开心 > 温柔 > 认真 > 平静`。

## 3. Lv2：拥有过去，也能够行动

### 3.1 Memory —— 信息生命周期，而不是 Vector DB
刻意不引入向量库，把生命周期做扎实。12 种记忆类型用 `slot` 区分性质：

| kind | slot | 说明 |
|---|---|---|
| `identity` | ✔ | 制作人的名字 / 职业 / 所在城市 |
| `preference` | ✔ | 喜欢 / 讨厌 |
| `relationship` | ✔ | 称呼、约定、态度转折 |
| `promise` | ✘ | **未来自己答应过要做的事**（跟踪是否兑现） |
| `experience` | ✘ | 共同回忆 |
| `self` | ✘ | 关于未来自己的记忆 |
| `fact` / `inference` | ✔ | 稳定事实 / **低置信度推断（2 天过期）** |
| `episode` | ✘ | 发生过的事件（含工具调用结果） |
| `transient` | ✘ | 易过期信息 |
| `reflection` | ✘ | 记忆巩固产生的高阶总结 |

**写（什么应该成为记忆）**：`MEMORY_PATTERNS` 把中文口语映射成结构化记忆，
例如「我叫可可」→ `identity/user.name`、「我答应你下次唱新歌」→ `promise`。
规则提取而非再调一次模型：快、免费、**完全可解释**。
有误匹配守门人（`_plausible`）——"我是**来**问的"不会被当成名字写进长期记忆。

**冲突处理（可修正，不累加矛盾）**：
- 同一 key 内容相同 → `reinforce`（强化，不产生冗余行）
- 同一 key 内容不同 → `supersede`：旧记忆标记 `superseded` 并指向新记忆
- 例：先说"名字是可可"再说"名字是小满"，只保留最新的，历史仍可审计

**回忆（什么时候重新想起它）**：多信号打分，每一项都写进日志：

```
score = 1.00·关键词重合 + 0.55·重要度 + 0.60·情绪加权
      + 0.35·新近度 + 0.20·频次 + 0.30·种类先验 (+ 意图提示 bonus)
```

- **情绪记忆加权**（创新点）：越有情绪的记忆越容易被想起 → 她"重感情"
- **回忆意图提示**：把"我叫什么"翻译成"去翻 `user.name` 槽位"，
  使关键回忆不靠字面重合碰运气
- 种类配额：避免 6 条记忆全是同一种
- 被想起会更新 `last_accessed` / `access_count` 并轻微强化重要度（**回忆本身有作用**）

**忘记与失效**：
- `/forget` 显式遗忘 = **软删除**（`status='forgotten'`），保留审计痕迹；
  且会**连被覆盖过的旧版本一起忘掉**（否则"要求忘记"只产生半个效果）
- `expires_at` 到期自动失效（推断类 2 天、易过期类 2 天）
- 按半衰期衰减（identity 3650 天 vs episode 30 天），
  琐碎且长期没人想起的记忆自动归档退出检索池

**记忆巩固（反思）**：`memory.reflect()` 把零碎对话总结成高阶记忆，
用本地模型做（不花 API 的钱），对应创新点「记忆巩固与反思」。

### 3.2 Action —— 可区分的"说过"与"做过"
`api_agent.py` 是一个真实的行动循环：

```
用户输入 → 模型决定（回答 or 调用工具）
        → tools.dispatch() 真正执行（带超时、错误封装、来源标记）
        → 真实结果作为 role="tool" 回传 → 模型基于结果继续
        → 直到给出最终回答
```

**"要不要行动"由谁决定 —— 三层，从零成本到最灵活：**

| 模式 | 行为 | 成本 |
|---|---|---|
| `keyword` | 只查关键词表 | 0 API 调用，但没命中就只会聊天 |
| `hybrid`（默认） | 关键词快路径；**没命中时让模型自己判断** | 未命中时约 0.5~1 秒 |
| `model` | 完全由模型判断，不用关键词表 | 每轮一次调用 |

关键词表的问题在于它**预设了"你会问什么"**。加上模型判断后，
像「明天要下雨吗」这种没写进词表的问法也能被正确识别为需要行动 ——
实测分类器在 8 组多样输入上全部判断正确（生日/偏好/回忆 → CHAT，
天气/计算/降雨 → ACT）。

- **来源可追溯**：每个工具结果都带 `source`（`open-meteo` / `system_clock` /
  `computed` / **`mock`**）、`executed_at`、`duration_ms`。
  真实数据源全部不可达时会**明确降级**并标注 `mock`，绝不冒充真实数据。
- **工具链**：循环允许连续调用多个工具（上限 `AGENT_TOOL_MAX_ITERATIONS`）。
- **审计"声称但没做"**：若整轮没有任何真实工具调用，而回复里出现
  "我查了一下"这类措辞，记一条 `action.claim_without_call`（warn）。
  这就是"说自己做了"与"真正做了"在日志层面的可区分性。
- **失败也会被说出来**：工具失败 → 真实结果回传模型 → 她道歉并说明失败；
  同时**影响角色状态**（心情 -0.12、活力 -0.10），对应开放问题 7。
- **副作用需确认**：`ToolSpec.side_effect` + `AGENT_ALLOW_SIDE_EFFECTS=false`，
  带副作用的工具默认被拦截并返回"需要确认"。

三个示例工具：
1. `get_weather` —— 真实 HTTP，`wttr.in → Open-Meteo → mock` 三级降级
2. `get_current_time` —— 系统时钟，支持有限时区（Windows 无 tzdata 时自动降级）
3. `calculate` —— **AST 白名单求值**，不使用 `eval`，拒绝任意代码执行

### 3.3 端到端数据流闭环
```
历史对话 ──提取──► 记忆 ──检索──► 注入 Prompt ──► 影响回复
                    ▲                                    │
                    └──────── 情绪状态 ◄─────────────────┘
                              ▲
        工具真实结果 ─────────┘（含失败 → 情绪受挫 → 回复带歉意）
```
每一环都有对应日志事件，可被 `--audit` 完整回放。

## 3.4 设计原则：不预设任何关于你的事
初版实现里塞了不少"预设"，被指出后逐条改掉了。现在这些原则是明确的：

| 曾经的预设 | 现在怎么做 |
|---|---|
| 假设用户叫某个名字（测试写进去的"可可"） | 记忆里没有名字就**先问**，绝不假设；`AGENT_USER_TITLE` 只是在得知名字前的占位称呼，可改可留空 |
| 一次性查询结果（天气/时间）写成长期记忆 | 默认**不写**。只有会改变未来行为的信息才值得长期保留 |
| 「你要记住我的名字哦」被抓成一条垃圾记忆 | 加了**纯指代过滤**：没有信息量的捕获直接丢弃 |
| 关键词表预设了"你会问什么"，没命中就只会聊天 | 关键词只当**零成本快路径**；没命中时**让模型自己判断**要不要行动（`AGENT_ROUTER_MODE`） |
| 用户说了新名字，但这一轮回复还在用旧名字 | 记忆提取移到**生成之前**：你刚说的话，她这一轮就能用上 |
| 问她自己的生日答不出来（生日明明写在人设里） | 把"关于她自己的确定事实"抽成**结构化短句**放进 Prompt，不再靠模型从散文里翻 |

> 测试也一并改了：`--test` 现在使用**临时记忆库**，不会往你真实的角色里塞任何数据。

## 4. 可观测性与审计

每轮一个 `trace_id`，所有事件带 `trace_id + turn + seq`，写入
`logs/agent_log.jsonl`（每行一个独立 JSON，可 `grep`/`jq`/`pandas` 读取）。

| 事件 | 回答的问题 |
|---|---|
| `route.decision` | 为什么走本地 / 走 API？命中了哪条策略、哪些关键词、置信多少 |
| `router.classified` | 关键词没命中时，**模型自己**认为要不要行动 |
| `context.built` | 用了多少轮历史、有没有摘要、注入了几条记忆、prompt 多长 |
| `memory.recall` | 检索到什么，**每条的记忆分数的分项构成** |
| `memory.write` / `supersede` / `forget` / `decay` / `expire` | 记忆怎么变化的 |
| `memory.tool_result_skipped` | 工具结果被**有意**排除在长期记忆之外（可审计这个决策） |
| `emotion.update` | 内部状态变化 + **可读原因** + 前后对比 |
| `action.call` / `action.result` | 调用了什么工具、入参、真实返回、耗时、来源 |
| `action.summary` / `claim_without_call` | 这轮到底有没有真的做事 |
| `llm.request` / `llm.response` | 模型、延迟、**首 token 延迟**、token 用量 |
| `llm.warmup` / `llm.retry` / `llm.truncated` | 冷启动预热、瞬时失败重试、输出被截断 |
| `speech.final` / `turn.end` | **她最终说了什么**、总耗时、首反馈延迟 |

一行命令回放：
```bash
python main.py --audit            # 最近一轮
python main.py --audit <trace_id> # 指定轮次
```

## 5. 三个创新点（按题目建议只挑少数做深）

1. **情绪记忆加权**（`RECALL_WEIGHTS.emotional_weight`）
   写入记忆时按当轮情绪强度打权重，检索时高权重优先 →
   她记得住的是那些有情绪的时刻，而不是流水账。

2. **工具拟人化包装**（`local_agent.revoice`）
   API 只负责"真的去查"和"把事实说准"，本地模型负责"用什么语气说"。
   模型被明确要求数字不得修改、不得罗列字段名；
   失败或模拟数据必须如实说明并道歉。

3. **主动消息**（`local_agent.maybe_proactive_greeting`）
   离开超过 24 小时后再次见面，她会先开口表达寂寞，
   并**顺手接上一条真实的高权重记忆**（答应过的事 / 共同回忆）。

另外实现了**记忆巩固（反思）**：每 N 轮把零碎对话总结成高阶记忆。

## 6. 开放问题的实际答案（代码里的取舍）

| 开放问题 | 本项目的答案 |
|---|---|
| 人格在 Prompt 还是状态？ | **两者分离**：核心自我在 Prompt（常量），当下的情绪/关系是显式状态（变量） |
| Agent 是否应有关于自己的记忆？ | **必须有**：`promise` / `self` / `experience` 三类专记她自己，否则会出现"昨天答应唱歌、今天问聊过什么"的人格断裂 |
| 是否需要建模关系？ | 需要，但**轻量化**：一个 `bond` 数值 + `relationship` 记忆类型，不建图数据库 |
| 事实 / 推断 / 经历是否用不同策略？ | **是**：`fact` 高置信永久，`inference` 低置信 2 天过期，`experience` 情感权重高、半衰期长 |
| 错误记忆如何修正？何时失效？ | 同 key 冲突→`supersede`（覆盖而非累加）；`expires_at` 硬过期；半衰期衰减；琐碎记忆自动归档 |
| 工具是否有价值？ | 工具**绝对优于** Prompt 的幻觉：查不到时她承认不知道，而不是编一个天气 |
| 行动失败是否影响角色状态？ | **会**：失败 → 心情/活力下降 → 回复带歉意（`action_emotion_deltas`） |
| 工具长时间运行怎么办？ | 工具状态提示本身就是"用户可感知的反馈"，并计入首反馈延迟（Lv4 的 10 秒要求） |
| 用户打断怎么办？ | CLI 单轮模型；流式输出下轮重新构建上下文。**未实现真正的打断**（见局限） |
| 工具结果是否进长期记忆？ | **默认不进**。一次性查询结果不会改变未来行为，只留在对话历史与审计日志里；值得记的是从中提取的稳定偏好。策略可配：`AGENT_REMEMBER_TOOL_RESULTS=none/transient/always` |
| 副作用操作是否要确认？ | 要：`side_effect` 标记 + `AGENT_ALLOW_SIDE_EFFECTS=false` 默认拦截 |

## 7. 运行方式

### 最省事：双击启动器
双击 `start.bat`（或在命令行敲 `start.bat`）。它会自动：
1. 检查 Ollama 是否在运行，没在运行就启动它并等它就绪；
2. 列出可用的本地模型；
3. 进入对话界面。

命令行参数会透传给 `main.py`，例如 `start.bat --test`。

> ⚠️ `start.bat` 里刻意只写**英文提示**：cmd.exe 按 OEM 代码页（中文 Windows 是 GBK）
> 解析 .bat 文件，写中文会导致命令被拆坏。中文输出全部由 Python 负责，
> Python 自己会切到 UTF-8，不受影响。

### 手动方式

## 9. Lv3：Live2D 表现层（已实现）

题目 Lv3 的要求是：
> "重点不在模型精度、动画数量或者画面效果，而在于：Agent 的内部状态能否通过身体
> 表现出来。……我们关注的是 Avatar 是否真正成为 Agent 状态的一种输出，而不是一个
> 独立播放动画的前端组件。"

### 9.1 怎么保证"不是独立的前端组件"

**前端不含任何状态决策**。整条链路是：

```
AgentState（心情/活力/羁绊/寂寞/害羞/关切）
   │  config.LV3_EXPRESSION_MAP  ← 映射表放在后端
   ▼
AvatarServer.push()  —— 决定 primary / layers / speaking / thinking / acting
   │  SSE（Server-Sent Events）
   ▼
浏览器：只负责把收到的参数插值过去，画出来
```

所以"她为什么摆这个表情"完全在后端可解释，也能写进日志
（`avatar.expression` 事件记录 mood / valence / arousal / route / 客户端数）。

### 9.2 情绪 → 表情的映射

模型自带 8 个表情。先用 `exp3.json` 反查它们各自驱动哪些参数，发现它们其实是
**开关参数**（`Param125`–`Param137`），于是得到真实可用的映射：

| 心情 | 主表情 | 叠加表情 | 含义 |
|---|---|---|---|
| 元气 / 开心 | `sing` 唱歌 | — | 她在唱 |
| 温柔 | `heart` 比心 | — | 亲近 |
| 害羞 | — | `blush` 脸红 | 脸红 |
| 寂寞 | — | `lean` 前倾 | 凑近想引起注意 |
| 认真 | — | `lean` 前倾 | 专注 |
| 闹别扭 / 低落 | — | `swirl` 圈圈 | 晕乎乎/闹脾气 |
| 平静 | — | — | 无表情 |
| **超开心**（valence≥0.8 且 arousal≥0.8） | `leek` 大葱 | — | 掏出标志物 |
| **正在查资料** | `swirl` 圈圈 | — | 她在努力 |

两个设计要点：
- `sing` / `heart` / `leek` 驱动的是**同一组**参数（133/134/135），互斥，
  所以只能出现在 `primary`；`blush` / `lean` / `swirl` 各用独立参数，可叠加。
- 判据里带**强度**而不只是种类：同样"开心"，特别开心时才会掏葱。

### 9.3 其他表现

- **口型**：`speaking` 为真时前端用一条有节奏的包络驱动 `ParamMouthOpenY`
  （没有真实音频，所以是"说话感"而不是精确对口型；Lv4 接上 TTS 后可换成音频振幅）
- **视线跟随**：`autoInteract: true`，鼠标移动时她会看你
- **状态胶囊**：思考中 / 查询中 / 说话中，直接对应 `thinking / acting / speaking`
- **内部状态面板**：左下角实时显示六个维度的数值和当前心情 ——
  这就是题目"可观测性"在表现层的对应物
- **字幕**：她说的最后一句话显示在底部

### 9.8 常见问题

**「模型加载失败：Network error.」** —— 这是最常见的坑，几乎都是**打开方式不对**：

浏览器**不允许 `file://` 页面读取模型文件**。如果你直接双击了
`live2d/web/index.html`，三个 `js/*.js` 能加载（相对路径的 `<script>` 被允许），
但模型是用 XHR 取的，会直接失败 —— 而且 file:// 下它会去找
`web/models/...`，那个目录根本不存在（模型在 `live2d/models/`，
只有通过服务访问时才会被映射成 `/models/`）。

**正确做法**：双击 `start_live2d.bat`，然后访问 `http://127.0.0.1:8765/`。

页面现在会自己识别这种情况并直接说明原因（不会再只丢一句 Network error）。

| 现象 | 原因 | 处理 |
|---|---|---|
| 提示"打开方式不对" | 用 file:// 打开了 HTML | 改用 `http://127.0.0.1:8765/` |
| 提示"连接不到表现层服务" | Agent 已退出（服务随进程一起停） | 重新 `start_live2d.bat` |
| 页面完全打不开 | 端口被占用后自动换了端口 | 看 Agent 窗口打印的实际地址，或对话里输入 `/avatar` |
| 忘了地址 | — | 对话内输入 `/avatar` |

排查入口：
- `/avatar`（对话内）：地址、已连接浏览器数、当前表情
- `http://127.0.0.1:<端口>/api/diag`：页面回报的渲染诊断（`modelSize`、`missingParams`、错误）
- `http://127.0.0.1:<端口>/health`：服务是否活着

## 11. 已知局限（如实记录）

1. **Python 版本**：题目建议 3.11+，本机是 **3.10.10**。
   所有代码兼容 3.10，功能不受影响，但未使用 3.11 的新特性。
2. **R1 的推理占用输出预算**：`deepseek-r1` 的思考过程计入 `num_predict`，
   短预算下会出现正文为空或被截断。已做三层防护：
   提高预算、`done_reason == "length"` 时裁掉半句话并告警、正文为空时自动重试。
   该模型不支持 `think=False`（会返回 502），因此无法真正关闭推理。
3. **`wttr.in` 在本机网络不可达**，天气实际由 Open-Meteo 提供；
   两个真实源都失败时会降级为明确标注的 `mock` 数据，不会伪装成真实天气。
4. **路由默认是混合模式**：关键词快路径 + 未命中时由模型判断。
   关键词那层仍可能误匹配（已对最容易误伤的天气组加闸），
   但漏判会被模型兜住。想要完全不依赖关键词表就设 `AGENT_ROUTER_MODE=model`；
   代价是**每一轮**都多一次 API 调用（本文档实测约 0.5~1 秒、很便宜但非零）。
5. **`deepseek-flash` 即使在极简单的分类任务上也会先产出约 90~100 个推理 token**，
   而推理计入 `max_tokens`。给太小（如 8）会 `finish_reason=length` 且正文为空 ——
   曾导致意图分类器把**所有**输入都判成"不需要行动"。现已给足 400 并加空正文兜底。
6. **冷启动会让第一句话失败**：首次调用要把 8GB 模型载入显存（15~30 秒），
   超过请求超时会返回 502，看起来像"她坏了"。已做三件事：
   显式放宽客户端超时、启动时预热、失败且未吐字时自动重试一次。
   另外 **Ollama 不会随程序启动**，所以提供了 `start.bat` 来兜住这一点。
7. **未实现真正的打断处理**：CLI 是单轮阻塞模型。
   若要做，需要把流式生成放到可取消的线程/任务里，并把"上一轮被中断"写进上下文。
8. **记忆提取用规则而非模型**：好处是快、免费、可解释；
   代价是表达方式超出模式范围时会漏记（例如"我平时不太碰咖啡"不会被识别为偏好）。
   规则也因此偏保守 —— 宁可漏记，也不要把垃圾写进长期记忆。
9. **API Key 是明文放在 `.env`**（已加入 `.gitignore`）。
   该 Key 曾出现在对话记录中，建议本题结束后到 DeepSeek 后台重置。
